# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository status

Split deployment, two different origins:

- **Frontend** — `index.html`, `nguoi-noi-ho.html`, `ho-so.html`, `tai-khoan.html`, `dat-don.html`, `freelancer.html`, `admin.html`, `report.html`, `assets/` — deployed to **Firebase Hosting** (`firebase deploy --only hosting`) at https://thayloimuonnoi-8d725.web.app. `firebase.json`'s `ignore` list keeps backend files (`server.js`, `src/**`, `package*.json`, docs) out of that deploy — the repo root doubles as both the hosting public dir and the backend's working dir, so don't assume everything at root is frontend-servable.
- **Backend** — `server.js`/`src/`, Node/Express + Firestore (`firebase-admin`) + payOS (`@payos/node`), deployed to **Render** (API-only, no static serving) at https://thayloimuonnoi.onrender.com, auto-deploys on push to `main`. CORS is locked to the Firebase Hosting origins (`server.js`) — a frontend change that needs a new origin (custom domain, etc.) means updating that list too.

`assets/api-client.js` calls the Render API by **absolute URL** (`API_BASE_URL` constant) since the two are cross-origin now — don't revert that to a relative `/api/...` path. payOS's `returnUrl`/`cancelUrl` (`src/payos.js`) come from `PUBLIC_BASE_URL`, which must point at the Firebase Hosting URL, not Render.

`assets/mock-backend.js` (localStorage-only fake backend) is no longer wired into any page — it's dead code kept around for reference, not a fallback. Don't resurrect it; if something needs fixing, fix the real path (`src/db.js` server-side, or the page's own `<script type="module">` client-side).

`assets/ui.css` is loaded by **all five pages** and holds the few things every page shows — the shared login popup and the toast. It defines no tokens of its own, reading whichever `:root` the page already set, which is what lets `index.html` load it without loading `app.css`. Anything needed on the landing page *and* the app pages belongs there, not in `app.css` (which `index.html` does not load) and not duplicated into `index.html`'s inline `<style>` (that copy has drifted before).

`assets/firebase-config.js` holds the public Firebase web config (safe to commit, unlike the server-side service account) — fill in real values there, not inline in pages.

## What this project is

"Thay Lời Muốn Nói" is a two-sided Vietnamese marketplace: a buyer pays a freelancer to place a phone call on the buyer's behalf, delivering a spoken message (confession, apology, congratulations, etc.) to a third party ("callee") who is not a user of the platform. Freelancers list their phone number and a voice demo; pricing is driven by word count, call duration, speaking speed, requested emotion, the freelancer's carrier per-minute rate, and desired call time.

[DECISIONS.md](DECISIONS.md) is the living spec/decision log, written in Vietnamese, kept so work can resume from a different machine with full context. It distinguishes decisions already locked in from points still open — **read it before making any product/business-logic change**, especially §5 (escrow/evidence state machine) and §8 (open items), since several things in the fake backend are explicitly-flagged placeholders (commission %, confirm timeout hours, admin passcode) rather than real decisions.

## Pages

The buyer flow mirrors comparable hire-a-person marketplaces (Playerduo, Cameo, Fiverr): browse with filters → profile → order form → order tracking. DECISIONS.md §14 has the reasoning.

- `index.html` — Noel-themed marketing landing page. Has its own illustrative price calculator (separate inline JS, not wired to real orders) — don't conflate it with the real pricing logic in `src/db.js` (`calcPrice`). Its "voices" section shows the real top four from the API, and it ends with an FAQ whose answers must keep describing what the system actually does.
- `nguoi-noi-ho.html` — public freelancer browse: filters, sort, voice samples on every card. Filtering is client-side (the list is fetched in full; no filter endpoint) and the filter state lives in the URL.
- `ho-so.html?id=<publicId>` — public freelancer profile with reviews and the share link.
- `dat-don.html` — "Đơn của tôi": wallet, and with `?f=<publicId>` the order form (callee name/phone, occasion, scheduled time, script, private note, options, live bill); orders in tabs with progress steps and cancel/confirm/dispute/rate actions.
- `tai-khoan.html` — "Hồ sơ của tôi": the account page for **every** user (buyer, freelancer, or both — one phone number is one account). Name (private, `GET/POST /api/me`), wallet and order counts, and the freelancer summary if they have a profile. Not to be confused with `ho-so.html`, the *public* freelancer profile.
- `freelancer.html` — freelancer dashboard: accept-orders switch, public profile link, stats, orders grouped by what to do next, profile + in-browser voice recording, withdrawals.
- `admin.html` — CSKH/admin: script moderation, dispute resolution, withdrawal approval, callee reports. Access is gated server-side by `ADMIN_PHONE_NUMBERS` (an env var on Render, checked in `src/authMiddleware.js`'s `requireAdmin`) — there's no separate admin login UI, just the same Firebase phone sign-in as everyone else.
- `report.html` — public, no-login form for a callee (the person who received a call) to report it.

## Working in this repo

- **Freelancers are identified publicly by `publicId`, never by phone.** Phone numbers are the Firestore doc ids for users/freelancers and stay server-side; everything public (`/api/freelancers`, `/api/freelancers/:id`, links) uses `publicId`. Don't add a field to `publicFreelancerView` without asking whether a stranger should see it.
- **Who sees what is decided in `src/routes.js`** — `publicFreelancerView`, `freelancerOrderView` (callee number only while `da_duyet_cho_goi`, script only in full after moderation, never the buyer's number), `buyerOrderView`. Hiding something in a page doesn't count: the data has already reached the browser.
- **Never spread a request body into a document.** `upsertFreelancerProfile` takes a whitelist (`profileFields`) — it used to merge the raw body, which let any account set its own balance. Prices are recomputed from the script and from option values checked against `PRICE_OPTIONS`; the client's own numbers are never used for money.
- `assets/catalog.js` holds the fixed lists people filter by (voice tags, regions, carriers, occasions), the order-status wording, and the shared freelancer card + voice player. The server only length-checks those values, so this file is the list.
- `src/db.js` is the single source of truth for business logic and the order state machine — it's a direct Firestore port of what used to be `assets/mock-backend.js`'s `TLMN.Order.*`, using `db.runTransaction` for anything that checks a balance before moving money (order creation, withdrawals). `src/routes.js` exposes it over HTTP and is also where request authorization lives (`assertOrderParty` checks the caller actually owns the order before letting them act on it) — don't move that check client-side.
- `assets/api-client.js` (frontend) mirrors `src/routes.js`'s endpoints 1:1 — add a method there when you add a route, matching names.
- `assets/firebase-client.js` currently uses a **temporary simulated OTP** (hands the code back instead of texting it, then mints a Firebase custom token — see DECISIONS.md §12) because real Phone Auth needs the Blaze plan. `mountAuthWidget({ onLogin, gate })` **builds and owns the single login popup the whole site shares** — no page carries login markup, and its look lives in `assets/ui.css` under `#loginDlg`, so changing the login means changing those two files and every page follows. Pages that require login pass `gate` (their `#auth` element), which then holds a short "đăng nhập để tiếp tục" card while the popup opens by itself; dismissing the popup leaves that card rather than an empty page, which is why the gate exists. `index.html` passes nothing, since browsing without an account is fine there — it gets its entry point from the header `#userBox`, which opts in with a bare `data-login` attribute. The widget fills that slot either way, with the phone number and a sign-out button once signed in. There is deliberately no `login.html`, and `getIdToken()` still returns a real Firebase ID token either way — `api-client.js` and `authMiddleware.js` don't know or care which path produced it. This is called out loudly in code comments — don't mistake it for the real thing, and don't build features that assume identity here is verified yet. Wallet top-ups, by contrast, are real (DECISIONS.md §13): only the signed payOS webhook credits a wallet, and only for an `orderCode` we issued with a matching amount — never add another code path that calls `creditTopup`.
- Edit [DECISIONS.md](DECISIONS.md) directly for any product/spec change; keep it in Vietnamese and follow its existing conventions: numbered `##` sections, bold for locked-in terms, `[CHƯA CHỐT]` inline markers for things explicitly not yet decided, and the `- [ ]` checklist in §8 for open items.
- The document's value is in separating settled decisions from open ones — when resolving something, fold it into the relevant numbered section (and cite the reasoning, as the existing entries do) rather than just deleting the open item.
- `npm run selftest` runs [api.selftest.js](api.selftest.js), [snow.selftest.js](snow.selftest.js) and [phone.selftest.js](phone.selftest.js). `api.selftest.js` boots the real `server.js` against an in-memory stand-in for Firestore/Auth/payOS and drives the API over HTTP — run it after any change to `src/`; it covers the money paths (escrow, refunds, payouts, price integrity), the profile whitelist, and what each audience can see. The other two lift code straight out of the shipped frontend files — snow that stops falling, and a phone number shape the login rejects — so run them after touching the canvas code or `toE164` — and note `firebase.json` has to keep ignoring `*.selftest.js`, since `public: "."` would otherwise publish test files to the live site.
- No frontend build step: edit HTML/CSS/JS directly. The backend only needs `npm install`; `npm start` runs it locally (needs a real or fake Firebase credential per `.env.example`, same as Render).
